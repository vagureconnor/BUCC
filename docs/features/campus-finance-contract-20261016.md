本文补充 BUCC 网费表单交接、应用内支付页与本轮只读观察。校园卡、网费的历史字段契约和官方页面证据见[校园财务契约摘录（2026-10-14，更新至 2026-10-15）](campus-finance-contract-20261014.md)。本文只记录端点、字段名和验证边界，不保留账号、验证码、Cookie、订单标识或原始网页。

## 网费表单与建单响应

网费表单从 `GET https://zfw.buaa.edu.cn/pay/card` 读取，依赖 BUCC 自己的 ZFW 会话。正式提交是对同一路径的 `POST`，使用表单编码，保留页面提供的动态 `_csrf-<id>`、`OneCardForm[cardNo]`、`OneCardForm[productId]`，并提交 `OneCardForm[amount]` 与本人输入的 `OneCardForm[verifyCode]`。验证码必须与本次金额一起提交；客户端不自动识别或复用旧验证码。

网费准备阶段由 BUCC 读取官方表单，保留动态 `_csrf-<id>`、`OneCardForm[cardNo]`、`OneCardForm[productId]`。原生界面继续收集金额和验证码；一次性表单 POST 交给 BUCC 内置 WebView 直接发往 `https://zfw.buaa.edu.cn/pay/card`。表单体由 `takeFormPost()` 在交接前消费，页面重挂载或失败后不重放。原始表单和 Cookie 仅使用 BUCC 自己的会话。官网对 POST 的响应及受允许的新窗口会在现有内置支付页中呈现；不再由原生后台先 POST，再抽取 `Location` 或 HTML 来寻找支付入口。

网费 POST 发出后，`prepare`/`create` 或 WebView 交接成功只代表流程交接，不代表订单建立。对响应内容、导航或新窗口的观察也不能单独证明订单建立、支付渠道可用、订单状态或已经付款。发生结果不明时停止，不重复提交。

校园卡仍沿现有原生 CAS 会话接续和官方支付入口流程进行；本轮网费表单直发不改变校园卡路径。用户已验证 BUCC 内置校园卡官网支付页可用，但没有付款；这只证明页面接续可用，不表示付款完成。

## 支付登录和 Cookie 边界

支付接续沿官方 `pass.cc-pay.cn/login`、`channel=BUAASSO` 与精确 CAS `service=https://pass.cc-pay.cn/login` 路径复用 BUCC 自己的 CAS 会话；`backUrl` 保持官方回调上下文。最终页面仍须是官方商城或收银台，不把支付登录页当成支付页。内置浏览器仅同步按支付 URL 域和 Cookie 安全属性匹配的 BUCC 自有 Cookie。

网费订单结果若不明确，尤其是 `CREATE_ORDER` 已提交后入口解析失败，必须停止并先复用已有页面、标签或只读记录。验证码或短信校验由本人输入。浏览器 DOM 证据、JVM 流程、HTTP 200、二维码图像和实际支付状态不可互相替代。

### WebVPN 会话边界

清理 ZFW 业务身份时必须保留共享 WebVPN gateway root、CAS 和其他业务所需 Cookie。网关可能重写官方表单 action 与验证码图片地址；表单和验证码解析必须基于当前网关返回的页面。内置浏览器 POST 继续使用当前 gateway 会话，并且仅对明确允许的响应内容执行严格解包。

SPOC `LocalSpocClient` 的凭据缓存现按连接模式、账号和认证时间隔离；scope 变化时会清除 Token、RoleCode 和纸飞机学生映射，再获取当前认证。`:shared:jvmTest` 中该 backend 测试类 22 项通过，包含模式切换、认证会话变化和并发读取刷新用例。该结果是本地测试证据，不能据此声称所有 VPN 问题已由实网验证解决。

用户随后明确反馈：网费和校园卡均能正常打开官方支付界面。该证据来自用户在已安装客户端的实际操作；不据此推断具体建单笔数、支付渠道选择、订单最终状态或实际付款。Agent 没有因此追加实网建单。

支付界面已打开后仍出现“请勿重复建单”的问题来自保留在后端的尝试标记。用户进一步明确要求：结果不明确时也允许主动重新建单，不作永久拦截。按此最新要求，新的 `prepare` 表示独立的新尝试：关闭旧准备状态、重置本轮尝试标记，再读取新表单和验证码或卡片上下文。原尝试的结果仍如实显示；不以 HTTP 200、导航完成或重新准备推断订单/付款状态。
